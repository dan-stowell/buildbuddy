# Making distributed-cache hinted handoff stop dropping work

Research snapshot: 2026-10-12. No PR was modified, commented on, or pushed. This document proposes changes; it does not implement them.

## Recommendation and meaning of “never”

The open PRs improve rolling-restart behavior, but do **not** make hinted handoff durable. After combining them with master, an acknowledged write can still lose its repair obligation through queue overflow, a local-write shortcut, holder process loss, shutdown exhaustion, source eviction, or incorrect completion accounting. Membership changes can strand or misdirect an obligation without explicitly dropping it.

A defensible guarantee is: **every acknowledged write creates the required number of durable, independently recoverable copies, and every missing-owner obligation remains durable until a current owner durably accepts it or a deliberate, versioned deletion supersedes it.** Implement this with durable admission, retained payloads, a recoverable delivery state machine, and membership-aware routing. It requires sacrificing write availability when capacity or durable replicas are insufficient.

Hints alone cannot promise unconditional data survival. Losing the holder's only disk while the intended target is down destroys a hint and its payload; a metadata-only hint on another node cannot reconstruct those bytes. With `W` independent durable payload copies, no eviction of protected data, and correct recovery, a write survives up to `W - 1` copy-destroying failures **before redundancy is restored**. Thus `W = N + 1` tolerates `N` such failures, subject to failure-domain placement and the storage assumptions. “Simultaneous” must include sequential failures within the unrepaired interval. Shared references to one object do not constitute `W` independent payload copies.

For a rebuildable cache, the likely best trade-off is reliable admission, restart recovery, bounded retained data with backpressure, and repair of hot data; full replicated hint storage and exhaustive anti-entropy should depend on measured miss/rebuild costs. Absolute retention during arbitrary outages effectively turns part of the cache into durable storage. Keep ordinary cache eviction as an explicit policy outside the protected handoff interval; do not describe a cache with ordinary eviction as permanently lossless.

## 2. Lifecycle after combining the PRs

1. **Choose write destinations.** `D-M:753` selects the replication-factor preferred peers and ordered fallback peers; `NewNodes` can select the extra ring, and same-zone placement can add a preferred destination. `PS-M:41` pairs each failed preferred peer with a successful fallback. It stops after three failed fallbacks (`PS-M:7,57`). If insufficient writers open, `D-M:2071` fails the write. Failure during streaming or commit also fails the overall write; this is not an acknowledged-write loss, though partial copies can remain.
2. **Write data to the holder.** Normal remote writers carry `handoff_peer`. The receiving proxy commits its underlying cache before `finishWrite` (`C-P:524,563`); reference writes likewise call `WriteReference` before completion (`C-P:537`). The CAS `AlreadyExists` shortcut now calls the hint callback (`C-P:491`). Local shortcuts are an exception, discussed below.
3. **Record the obligation.** `D-P:643` keeps a resource name plus the original context in a channel keyed by destination address. Capacity defaults to 100,000 entries **per peer** (`D-P:74`). It stores no payload in the hint and persists nothing. Admission is nonblocking and may return false.
4. **Acknowledge.** `C-P:563` checks acceptance only when `require_handoff_accepted` is true. `RemoteHandoffWriter` sets it (`C-P:1190`), whereas ordinary `RemoteWriter` and `RemoteReferenceWriter` do not (`C-P:1179,1204`). The normal write path uses those ordinary writers. `D-M:1838` waits for all opened writers' commits; this is not majority quorum arithmetic despite the nearby “QUORUM” comment. It requires at least the configured replication-factor writer count, but counts successful cache commits, not independently fsynced copies plus accepted durable hints.
5. **Schedule and deliver.** Every heartbeat cycle iterates the main ring, and a successful heartbeat starts a handoff worker (`D-P:747`). The worker removes an item from the channel before delivery (`D-P:733`). `D-P:696` retains request values but ignores request cancellation. `D-P:1327` first checks destination presence, otherwise opens the holder's local reader, streams bytes, and commits the remote writer. There is no fetch-from-another-replica fallback here.
6. **Complete or retry.** Success consumes the item and increments `delivered`; missing local source consumes it and increments `dropped_source_missing` (`D-P:708`). Other failures attempt a nonblocking requeue (`D-P:675`). There is no durable receipt, delete record, hint TTL, enqueue timestamp, or maximum retry count.
7. **Shutdown.** `D-P:806` stops heartbeat work, waits for workers, stops inbound RPCs, then drains queues. `D-P:850` retries direct delivery for a two-second period per peer queue, then `D-P:902` forwards the payload and obligation to another main-ring peer. The shared shutdown deadline bounds the process; failures or leftovers are dropped. Forwarding migrates an in-memory obligation; it does not replicate it durably.

### What the PRs actually eliminate

#13745/#13746 eliminate the unconditional CAS-dedupe omission **if** admission succeeds. #13746 eliminates master’s unconditional consumption on transient send error **if** requeue succeeds. Detaching request cancellation prevents a finished client RPC from prematurely bounding future delivery; a fresh attempt deadline still applies. Shutdown draining/forwarding reduces graceful-restart losses, and required acceptance prevents successful shutdown transfer to a full queue when the receiver implements the new protocol. #13741 shortens disconnected-peer recovery exposure.

They do not close any of L1–L14 end to end. A missing callback still returns true in `C-P:554`; mixed-version peers ignore the new proto field and can acknowledge forwarding without enforcing admission. Require a protocol capability/version check for a strict rollout. Master's newer proxy shutdown/listener handling already covers the start/shutdown nil-server race addressed in the older PR branch.

There is no evidence here of periodic inter-peer anti-entropy. Master has read-triggered backfill (`D-M:1272,1305,2167`) and backfill metrics. It repairs eligible earlier missing preferred peers when a later peer yields data; it excludes failed peers and is best effort. A successful first preferred read need not check missing later replicas. Cold data, unreachable peers, changed ownership, and fully missing blobs remain unrepaired. Pebble's local background repair is not distributed replica synchronization.

## 4. Design: close the gaps as one protocol

### A. Durable obligation plus retained payload

Use a dedicated persistent journal/DB outside ordinary evictable metadata. Each record contains operation ID, tenant/group and isolation, resource identity (digest function, digest/size, cache type, instance and representation as needed), mutable version or tombstone, payload locator/generation, logical shard and owner epoch, creation time, state, and retry scheduling information. Persist security identity sufficient for authorized service replay; do not serialize a Go context or retain its expired bearer credential as the recovery mechanism.

Commit sequence:

1. Reserve hint count **and retained bytes**, with per-tenant/global limits. Reserve space for journal overhead and recovery. A record in flight still consumes its reservation.
2. Stage and verify payload. Hold an atomic retention reference or write a dedicated spool object. For deduped CAS, atomically verify and pin the existing durable object before treating it as a copy. For references, retain object lifetime, metadata, and access/decryption capability; multiple independent clones versus a shared object must be counted correctly.
3. Make payload and locator/index durable, then persist/fsync the obligation and pin bookkeeping. With separate payload files and DB, use an ordering/recovery protocol, including durable file publication; a single DB batch cannot atomically fsync unrelated files. A crash before admission can leave a collectible orphan but cannot leave an acknowledged promise pointing to undurable data. For inline data in one store, combine data, pin, and hint in an atomic synced batch.
4. Return a durable acceptance receipt. Overall write success waits for the configured independent-copy threshold. Every local, byte, reference, and AlreadyExists path participates. A hinted writer must fail closed if a nonempty obligation has no callback or the peer lacks durable-admission capability.

Group commit can amortize fsync, but success must wait for the batch's durability. Rebuild the pending index on restart before admitting conflicting deletes/evictions. Detect journal corruption, and recover from replicated state where available rather than silently discard records.

### B. Backpressure and write success policy

Finite disk, unlimited writes, arbitrarily long outage, and no drops cannot all coexist. Reserve quotas before accepting bytes where possible. On admission failure, retry a different eligible holder using a retained/replayable input; otherwise return ResourceExhausted/Unavailable. Existing streams may not be replayable, so write failure is a valid first implementation rather than complicated transparent failover.

Use sloppy quorum precisely: count a holder's **durable retained payload plus durable repair obligation** as one write placement, or a durable owner copy as one placement. An obligation without a recoverable payload is not a copy, and one node serving several logical obligations is still only one failure domain. Require `W` distinct durable placements; if the promise is full replication-factor durability, choose `W` equal to that factor. A lower `W` improves availability but weakens the stated guarantee. Existing master already waits for all selected commits and fails insufficient opening; change the meaning of a counted commit before adding configurable quorum arithmetic.

### C. Pinning and data lifetime

Use persistent refcounts or reachability from live obligations, keyed to immutable object generation. Multiple pending hints share one CAS payload pin. Delivery and eviction must synchronize through the backend's key lock/transaction; “check then pin” and “check then evict” are insufficient. Pins cover metadata, file/object bytes, shared-object lifecycle, and encryption key availability.

A separate spool is easier to isolate from cache janitors and migrations, at the expense of another payload copy. A filesystem hardlink can retain an immutable file cheaply, but does not retain inline/GCS data, metadata, mutable snapshots, or survive disk loss. Selective pinning inside Pebble is more efficient but affects eviction, delete, orphan cleanup, reference ownership, and shutdown/recovery paths.

Release a pin only after durable completion or a deliberate versioned supersession/delete. A crash before release can leak retention; recovery can safely collect it. A crash before durable completion must cause replay, not early unpinning.

### D. Retry, receipts, membership, and concurrency

Records transition `pending → leased/in-flight → completed` or back to pending. Dequeue is a scheduling action, never obligation deletion. Leases expire on worker/process failure. Target applies an immutable digest or conditional mutable version durably before replying. Persist source completion after the receipt; completion fsync can be batched because replaying an already delivered CAS item is safe. Forwarding uses the same transition with a durable next-holder receipt and keeps source responsibility until that receipt is accepted.

Use limited per-peer/per-tenant workers, fair scheduling, jittered backoff, and byte-sensitive deadlines. Heartbeat is a scheduling hint, not the authority for which durable records exist. Retry pending records even when their recorded destination disappeared from current membership. Recompute required owners on epoch changes; durably establish obligations for the new owner set before discarding obsolete ones. Use node incarnations and avoid interpreting success from an old address as current-owner coverage.

For AC, versioned conflict resolution and tombstones are prerequisites for convergence; digest-idempotency alone is insufficient. Reject stale replay, and define whether newer accepted writes supersede older obligations. Tombstone garbage collection requires confidence that old replay cannot resurrect deleted data—an epoch fence or bounded stale-operation policy, not an arbitrary tombstone TTL.

### E. Replication and anti-entropy

Replicate obligation metadata if the requirement includes losing a holder disk. Also replicate or durably externalize the payload; metadata replication alone only makes missing-data failure observable. Choose failure-domain-aware placements. A replicated log without election/fencing can replay twice; CAS tolerates duplicate replay, but mutable ownership and completion need fencing/version rules. A surviving copy must be able to rediscover missing owner coverage even if the original coordinator vanished.

Add periodic range inventories or Merkle/digest-range reconciliation among current replicas, including known fallback holders and migration ranges. Compare full isolation/key identity; mutable inventories include versions/tombstones. Inventory APIs, checkpoints, bandwidth limits, and verified payload repair are new work. Independent eviction causes persistent differences, so define a retention/live-set window and avoid endlessly recopying intentionally evicted cold data. Read repair remains a cheap complementary path, not a universal backstop.

Anti-entropy promises eventual repair **only when at least one readable source survives, ownership/connectivity stabilizes, authorization remains possible, and scan/repair throughput outruns churn**. It cannot reconstruct data lost from every copy, undo unrecoverable corruption, recover inaccessible encryption keys, or distinguish a valid deletion from missing data without deletion/version metadata. Hints alone also cannot repair a target disk wiped after hints already completed; a retained replica plus anti-entropy or read repair is needed.

## 5. Costs and sizing

These are engineering estimates to validate on the intended hardware, not measured benchmarks. Latencies on local SSD can be sub-millisecond to a few milliseconds for a sync, but tail latency and network volumes can be much worse. Write fanout runs in parallel, so the added critical path is generally the slowest required durable placement, not the sum of every peer's sync.

Let `λ` be newly admitted distinct obligations/s, `T` their residence/outage seconds, `h` serialized metadata bytes/record, `b` mean retained payload bytes, and `μ` delivered obligations/s after recovery. Pending records are about `λT`; journal space is at least `λTh` plus indexes/WAL/compaction, and retained payload is approximately `λTb` before dedupe. At 1,000/s for one hour, 3.6 million records at an illustrative 512 B each need 1.84 GB of raw metadata; 100 KB of distinct payload per record needs about 360 GB. Recovery requires `μ > λ`; drain time is approximately backlog divided by `μ - λ`. Measure actual serialized sizes and tenant skew.

## 6. Incremental implementation and measurement plan

Order below prioritizes prevented loss per effort. CAS should reach a well-defined durability contract before adding full mutable-cache convergence.

1. **Establish observability and integrate PR mitigations.** Reuse #13745 dedupe fix, #13741 reconnect tuning, and #13746 retries/shutdown/events. Retain master's newer proxy shutdown code. Add pending and in-flight gauges, oldest age, delivery latency/attempt/error metrics, and local-path instrumentation. Deploy with staggered restart soak tests. Exit criterion: reconciliation of event counts and known forced drops; no unexplained missing obligations. These improvements reduce routine exposure but must still be called best effort.
2. **Close deterministic admission holes.** Common hint-aware commit for local/remote, byte/reference/dedupe writes; require acceptance for every hinted placement, fail closed on absent callback/unsupported peer, and reserve capacity including in-flight work. Coalesce CAS repeats. Fault-inject full queues and concurrent requeue/admission. Exit criterion: no successful hinted write without accepted obligations; failed writes are measured distinctly. This removes L1/L2/L5 locally, but accepted RAM hints still disappear on crashes.
3. **Implement durable CAS spool/log and replay with strict copy accounting.** Integrate payload retention and log admission rather than shipping a metadata-only “durability” claim. Audit backend fsync/index semantics; use synced payload/metadata/pin boundaries and durable IDs. Initially reject writes that cannot obtain the configured durable placement count. Completion uses durable receipts; scheduling leases survive process failures. Exit criterion: crash at every commit/receipt boundary, restart with retained disk, and find every acknowledged obligation pending or completed with a valid retained copy. This closes routine restart/deadline/source-eviction paths L3/L4/L6/L7 and receipt-loss effects under the stated disk-survival model.
4. **Handle age, membership, and replay authorization.** No hint TTL in strict mode; tenant/byte quotas bound admission instead. Add epoch/current-owner rerouting, extra-ring scheduling, node incarnations, fair retries and adaptive transfers. Test target absence longer than former cache residence, target replacement, ring migration, oversized blobs, and expired original request credentials. Exit criterion: pending obligations survive and eventually converge after recovery; no hints orphaned outside the heartbeat ring. Deliberate operator abandonment is explicit, audited, and weakens the promise.
5. **Add failure-domain durability if the business requires it.** Replicate retained payload/obligation state or use a durable external spool with a stated external durability contract. Kill/delete holder volumes and whole failure domains. Exit criterion: `N` lost copy domains during the repair window preserve readability and reconstruction for `W=N+1`; `W` losses produce a detected unrecoverable outcome rather than a false success claim.
6. **Add versioned AC/deletion semantics, then anti-entropy where justified.** Until AC conditional/versioned replay exists, limit the strict guarantee to immutable CAS and explicitly scoped deletions. Improve read repair coverage cheaply, then add rate-limited range scans for cold/migrated data if measured under-replication merits it. Exit criterion: reordered deliveries/deletes cannot resurrect stale values; seeded divergence with one surviving source converges within the repair SLO, while all-copy loss is reported as unrecoverable.

### Metrics and accounting

#13746 already proposes `buildbuddy_remote_cache_distributed_cache_hinted_handoff_count{event=...}` with `queued`, `delivered`, `requeued`, `forwarded`, `dropped_queue_full`, `dropped_source_missing`, and `dropped_at_shutdown` (`server/metrics/metrics.go` in the PR). Master already has backfill count, byte, and latency metrics, but no equivalent handoff lifecycle counter. Neither has a hint-expired counter because neither implements hint expiry.

Extend rather than replace these metrics:

- **Created/admitted:** distinguish attempted creation, durable admission, coalescing, and rejected admission. Count logical obligations separately from retry attempts and forwarded physical records. A rejected write is not a successfully admitted hint being dropped.
- **Delivered/completed:** distinguish target write, verified-existing durable copy, superseded version, acknowledged transfer to holder, and owner reroute. `forwarded` is not owner delivery. Use an operation ID for state reconciliation; keep IDs/digests out of Prometheus labels.
- **Dropped:** bounded reason labels such as queue overflow, source missing, shutdown deadline, journal corruption, lost holder volume, policy abandonment, unsupported peer, and irrecoverable-all-sources-missing. Abrupt crash cannot emit a reliable final counter from the dying process; reconstruct unresolved admissions from durable state/replicated audit and monitor restart gaps.
- **Expired:** add `expired{reason=hint_ttl|payload_ttl|policy_retention}` when such a policy exists; strict hint TTL expiry must stay zero. Record a versioned deliberate delete as `superseded/deleted`, not an accidental loss. Missing data should carry storage tier and suspected cause when knowable; do not guess “expired” from every NotFound.
- **Gauges/histograms:** pending/in-flight records and bytes, pinned/spool bytes, oldest age, admission wait and fsync latency, end-to-end delivery lag, retry attempts/error classes, reroutes, duplicates, under-replicated retained keys, scan lag and repairs, failed writes due to durability/capacity. Avoid unbounded raw target-address/group labels; expose per-target diagnostics through bounded operational views.

Within each durable ownership scope, admissions should reconcile to pending + in-flight + completed + transferred-out + explicit terminal policy outcomes, adjusted for transferred-in. Requeued is an attempt event, not another admission; gauges include records removed from the RAM scheduling queue. Coalescing and tombstone supersession need their own ledger transitions. The PR counters alone cannot prove this invariant and can lose increments on process death.

Benchmark hinted versus unhinted paths for p50/p95/p99 write latency, throughput, disk sync/IOPS, bytes written, RSS, spool growth, drain rate, read misses, and rebuild cost. Run a fault matrix across process kills, power-loss/storage fault simulation, disk deletion, full capacity, lost responses, long outages, membership churn, and mutable reorder/delete races. PR rolling-restart tests use a surviving local-cache object (including an in-memory test cache); they validate behavior under their scenarios, not physical fsync, disk-failure tolerance, or indefinite-outage survival. No benchmark or test suite was run for this document; claims derive from source review and temporary patch composition.

## Decision

For ordinary cache deployments, take the PR mitigations and admission/local-path fixes immediately, then build a durable, quota-bounded CAS handoff spool that retains its source and fails writes when it cannot keep the promise. Measure whether replicated spool storage and cold-data anti-entropy save enough rebuilds to justify their cost. Keep deliberate cache retention policy explicit.

If the requirement literally includes holder disk destruction and concurrent target outage, require independent durable payload placements plus recoverable obligations; hints alone cannot satisfy it. If the requirement includes mutable data and deletes, versioning/fencing/tombstones are also essential. The achievable contract is conditional durability and eventual repair with surviving data, not “never lose anything” under unlimited failures, unlimited writes, and finite storage.
