# Landable series: direct OCI fetching from the cache proxy

## End state and evidence
The executor can choose a remote OCI fetcher on its cache target or an in-process fetcher that contacts registries itself; both reuse the OCI service caching implementation, with executor caching controlled separately. The cache proxy can fetch directly into its local AC/CAS for experiment-enabled groups, falling back to the apps on selected failures before any blob bytes are sent; bypass-registry requests still go to the apps. Shared HTTP transports reduce connection churn across these paths.

## Gaps and risks before landing
- **Auth:** draft proxy tests use anonymous/public registries and fake apps; they do not establish private-registry authorization or tenant isolation. Request credentials are forwarded to the existing service, not newly discovered on the proxy. Check executor-resolved credentials, bearer refresh, credential rotation/access-proof TTL, local AC namespace and internal-hop metadata/client identity. Never use trusted `NewLocalServer` for proxy requests; #13772 correctly uses `NewServer`.
- **Gating/startup:** #13772 evaluates its experiment with default false but constructs the service eagerly whenever local AC exists. #13763 eagerly initializes and unconditionally replaces the local Resolve path; it supplies no rollback flag. Registry settings still have `executor.*` names (mirrors and private-IP allowlist) on the proxy: explicitly document/configure them and egress, DNS, proxy env and TLS trust. `ocifetcher.enabled` gates registration, not direct constructor use.
- **Streaming correctness:** #13772 acknowledges sends can outlive `FetchBlob` due to singleflight cancellation. An atomic counter prevents a counter race, but a load/check is not synchronization with an in-flight `Send`; the old request's stream can still be used after return. Require cancellation/concurrent-waiter tests and a stream-lifetime fix before 8. A failed Send may also have ambiguous delivery; do not treat every failed Send as safe to replay.
- **Fallback:** 401/403 fallback may accommodate registry IP policy but doubles work for invalid credentials; 429 can amplify throttling. Blob fallback treats *all* pre-byte Internal errors as registry read failures, potentially hiding cache/programming errors. Narrow provenance, avoid retrying cancellation/deadline exhaustion (registry error conversion can map non-HTTP errors to Unavailable), and bound total retry latency. NotFound intentionally does not fallback; document this and test each method.
- **Cache and integrity:** service singleflight relies on successful cache population for waiters, unlike uncached local calls. Test cache write failure, eviction, partial read and cross-tenant concurrency; ensure trusted metadata cannot produce corrupt cache entries. Local bypass still resolves tags and fetches misses, whereas remote bypass is strict cache-only: update method comments that currently describe only remote semantics.
- **Metrics/operations:** fallback counter exists, but lacks direct-attempt/success denominator, route latency/bytes and cache-hit visibility. Group × registry × method × status labels can be expensive; agree cardinality limits, dashboards and rollback thresholds. Confirm apps' fallback capacity and avoid logging secrets from registry errors. Transport reuse retains mirror layering; test auth separation and connection pooling without mutating the shared client.
