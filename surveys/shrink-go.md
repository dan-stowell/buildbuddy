## 1. Summary: five biggest wins

These are estimates from import and module graphs, not measured binary-size or clean-build improvements. “Direct reduction” means fewer first-party module requirements; a dependency can remain indirect. Generated repository removal also requires checking other Bazel modules' requirements.

### Test-only, tool-only and duplicate jobs

* Exactly **3 direct modules occur only in `_test.go` files**: porcupine (1 directory/1 file), etree (1/1), faker (2/2). These are test-build costs, not server-binary costs. Etree and porcupine have substantive XML/linearizability jobs; only faker is an attractive replacement candidate.
* Tool directives: smarter-device-manager, difflib, gorilla/mux, exhaustive, x/tools/go/analysis, staticcheck, otiai10/copy, telemetry/counter. There are **8 directives**, many backed by requirements marked indirect. `tools/deps/deps.go` is build-tagged `tools` and retains vtprotobuf and API annotations intentionally. vtprotobuf also has a generator importer. API annotations' only source importer is this tools file, but `proto/BUILD` consumes the repo. Neither is dead.
* `go-cmp`, `testify`, `goleak`, Selenium and rules_webtesting also appear in non-test-filename helper code. For example `server/testutil/webtester/BUILD` explicitly says `testonly = 1`; do not classify these as production simply because their helper filename ends `.go`.
* YAML: **4 parser module paths** (`gopkg.in/yaml.v2`, `.v3`, `go.yaml.in/yaml/v2`, `/v3`) plus `sigs.k8s.io/yaml`. First-party source imports: 8 directories for old v2, 6 for old v3, 1 for sigs, **0** for either new go.yaml path. Transitive upgrades won't eliminate old first-party paths automatically.
* JSON: json-iterator/go and goccy/go-json are indirect; **0 first-party source imports each**. No direct JSON-library removal task to hand out.
* Logging: zerolog (7 directories/8 files) is central; logrus (1/1) is required by Firecracker's SDK-facing logger adapter. zap, logr, stdr and glog are indirect. A logrus import replacement alone cannot satisfy that SDK interface or eliminate its transitive requirement.
* JWT/JWK: jwx (1/1) versus golang-jwt/v4 (12/18) is a real consolidation candidate. go-jose/v4 remains required by OIDC/SAML; do not claim all JWT-related modules disappear.
* LRU: Hashicorp v1 has 2 first-party directories, v2 has **0** first-party imports. The repo's generic `server/util/lru` supplies the same basic cache job. V1 still has 8 selected-module parents, so consolidation demotes it rather than removes its repository.
* Process inspection: go-ps and gopsutil each have the same 2 first-party directories (`commandutil`, `procstats`); gopsutil also supplies process stats and Windows support. Using gopsutil for enumeration avoids a first-party duplicate; go-ps remains in godemon's module requirements.
* UUID: google/uuid has **36 directories/36 files**, and 51 selected-module parents. This is not a useful “replace two call sites” win; indirect ULID solves a distinct job.
* Retry: source uses `server/util/retry`; backoff/v5 and lestrrat backoff/v2 are indirect with **0** first-party imports. The latter can disappear with jwx, subject to graph verification.
* Cloud/SQL: AWS v1/v2 coexist, GCP services are separate nested modules, and SQLite has intentional cgo/nocgo implementations. The existence of multiple module paths does not establish redundant functionality.

## 4. Not worth it / blocked

* **Wholesale SDK/database removal:** compute is only tools/edit_instance_template, but it edits actual cloud instance templates; storage has 2 real backends, secretmanager 1 secret backend, Azure 1 blob backend. SQL drivers are runtime choices, not dead declarations. Keep supported features unless an owner explicitly retires them.
* **SQLite consolidation:** db_cgo.go uses mattn/go-sqlite3; db_nocgo.go uses ncruces/driver and embed (WASM). Build tags show why both exist. Dropping either loses a supported build variant; not a small dependency cleanup.
* **VictoriaMetrics → Prometheus:** tempting because only monitoring imports it and calls WritePrometheus once, but Dragonboat imports it in event.go and internal/transport/metrics.go. Removing the call would silently drop Raft metrics, and its module stays transitive. Reject a blanket replacement.
* **AWS v1 “just change imports”:** Tink awskms v2.1.0 requires AWS SDK v1.49.21 and uses v1 KMS interfaces; current source creates the v1 session/KMS client. Additionally flagd/core's selected go.mod requires AWS v1.55.6 indirectly, even though a source search of flagd/core itself has no AWS-v1 Go imports. Therefore even the adapter task does not guarantee removing its generated repository or 329M source tree. Migration is useful for binary/package consolidation only after measuring actual selected closures.
* **Firecracker logrus/cpuid:** logrus is passed through the SDK's logger interface, not used as an independent application logging framework. cpuid reads vendor/family used in VM behavior; CPU identification is not simply available from runtime.NumCPU. Both remain transitive SDK/compression dependencies; changing one import is not a repository-removal win.
* **Generic glob replacement:** workspace uses gobwas brace alternatives in CleanInputs; filepath.Match does not match that syntax. Replacing it requires defining and preserving the public pattern grammar.
* **pkg/errors → errors import swap:** status exports its StackTrace alias and Frame types, and log formats them. Stdlib errors does not implement that interface. The scoped task is a compatibility-sensitive redesign, not two call sites and a mechanical replacement.
* **Sigs YAML → v3 import swap:** Atlas has one sigsyaml.Marshal(u.Object) call, but sigs marshals through JSON and uses JSON field semantics. K8s modules keep sigs transitively (9 selected parents). Too little gain for changing manifest semantics; exclude from the ranked backlog.
* **YAML v2 → v3 mechanical sweep:** cli/translate/yaml depends extensively on MapSlice, which v3 removes. Split its rewrite from structured callers and test YAML 1.1 scalar behavior. Do not try to eliminate all four YAML paths by pinning one replacement; upstream APIs differ.
* **UUID/semver/retry rewrites:** UUID has 36 importers; Masterminds semver has 5 directories and range/version behavior; first-party retry already has its own implementation. Reimplementing mature semantics yields low gain, and upstream modules keep alternatives.
* **Porcupine/etree/testify:** test-only cost is real but porcupine checks Raft linearizability, etree builds SAML test XML, and testify is pervasive. Their jobs are not duplicated by stdlib without substantial test churn. Faker is the narrower test-only opportunity.
* **Gazelle/buildtools/tools “unused” declarations:** CLI fix imports both old Gazelle APIs and the v2 compatibility path from the same Bazel Gazelle repo. Tool directives and tools/deps retain lint/protobuf infrastructure. Root go.mod has no zero-import direct modules. Removing tool dependencies without exercising bb fix/lint/pbsync would break workflows.
* **Jaeger exporter retirement:** it is version 1.17.0 alongside OTel core 1.47.0, but remains selected by app.trace_jaeger_collector. Retirement would remove 1 direct module, but usage/config migration is unknown; do not silently delete a supported flag. Split into a later owner-approved feature retirement rather than an engineer's independent cleanup.
* **Full build and binary-size claims:** single-target Bazel build timed out; there are no before/after clean builds or linked-size measurements. Quantified import, module, repository and package counts are the usable baseline. Each implementation PR should build its actual server/executor/CLI binary and compare sizes with the same toolchain and flags.
